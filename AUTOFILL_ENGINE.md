# Движок автозаполнения банковских выписок — v2

> Контекст-документ для продолжения работы (в т.ч. в Claude Code).
> Описывает архитектуру, текущее состояние и дорожную карту движка, который при
> загрузке выписки автоматически проставляет операциям счёт, статью ДДС, статью
> расхода и контрагента, а для эквайринга-свода разворачивает строку в две
> операции. Цель — «как 1С»: постепенно учить систему по виду платежа и
> назначению, с универсальными правилами в коде и тенантными правилами, которые
> настраивает пользователь через UI.
>
> **v2 (обновление):** добавлены статья расхода (`default_expense_id`), UI
> управления правилами и разноской, ИНН в выписке, сплит эквайринг-свода Т-Банка
> на две операции, выборочное создание операций. Подробности — в §9 и §10.

## 1. Главная идея — двухступенчатая модель

Разноска строки выписки разбита на две ступени, как «Вид операции» в 1С:

1. **Классификация: сигнал → категория.** Категория — строка-идентификатор
   (`TRANSFER`, `CUSTOMER_PAYMENT`, `ACQUIRING_FEE`, …), связывающая правило с
   разноской. Универсальные правила (в коде) выдают категорию без тенантных id,
   поэтому переносимы между тенантами.
2. **Разноска: категория → счёт + статья ДДС + контрагент.** Здесь уже тенантные
   id (статьи ДДС у каждого свои). Настраивается один раз (UI или сидер).

Связь правила и разноски — **по строке категории**. Несколько правил могут вести
в одну категорию; счёт/статья для категории меняются в одном месте (в разноске).

Зачем так: статья ДДС у каждого тенанта своя, универсальное правило не знает
тенантных id. Оно выдаёт категорию, тенант мапит категорию на свою статью.

Источники правил классификации (тенантное бьёт универсальное):
- **Универсальные** — в коде (`classify()`): сейчас только `is_self_transfer` →
  `TRANSFER`. Верны для всех, не требуют разметки.
- **Тенантные** — в таблице `payment_classification_rules`, наполняет пользователь
  (теперь через UI, см. §9).

## 2. Ключевые архитектурные решения (НЕ переоткрывать)

- **Статья ДДС (тип `flow`) живёт ТОЛЬКО на денежной ноге А100.** У А100
  `info_1=cash, info_2=flow`. У расходных счетов (П589) `info_1=expenses`, поля
  под ДДС нет. Поэтому `flow_info_id` из разноски кладётся на А100-ногу, а
  `counter_account_code` — на корр-ногу.
- **Статья расхода живёт на info_1 корр-ноги расходного счёта (П589).** Берётся из
  `info.default_expense_id` той статьи ДДС (flow), что подставлена. См. §9.1.
- **Перевод между своими счетами** определяется в ПАРСЕРЕ: `ПлательщикИНН ==
  ПолучательИНН` внутри документа. Парсер ставит `is_self_transfer`. Перевод =
  А100↔А100, «Перемещение денег» на ОБЕИХ ногах (иначе не схлопнётся в ОСВ).
- **Правила НЕ засеваются.** `payment_classification_rules` рождается пустой,
  наполняет пользователь (в будущем — автообучением).
- **Разноска (`category_postings`) может засеиваться** — настройка «куда
  проводить», тенант переопределяет.
- **Счёт в разноске — по КОДУ, не по id.** Коды плана счетов (А100, П589, А405,
  П587) общие для всех тенантов → разноска ссылается по `counter_account_code`,
  матчер резолвит code→id на стороне тенанта (`biIdByCode`). Статьи ДДС — по id
  (у каждого свои). **Решение подтверждено повторно** (был заход переводить
  разноску на id — отклонён ради переносимости/сидеров/автообучения).
- **`PaymentCategory` — НЕ справочник, а две системные константы.** В v2 класс
  урезан до `TRANSFER` и `OTHER` — только то, на что опирается код. Бизнес-
  категории (`CUSTOMER_PAYMENT`, `ACQUIRING_FEE`, …) живут в БД как свободные
  строки, заводятся правилами/разноской/сидером. Валидации `isValid()`/`ALL`
  больше нет — категории создаются свободно (по плану — и автообучением).
- **На старте — только подсказка, не тихое проведение.** Человек подтверждает.

## 3. Системные категории (`app/Services/PaymentCategory.php`)

Класс сведён к двум константам, на которые опирается КОД матчера:

| Константа | Назначение |
|---|---|
| `TRANSFER` | перевод между своими — ставится в коде (universal), до правил |
| `OTHER` | ни одно правило не сработало → ручная разметка |

Всё остальное — категории в БД (`category_postings.category` + правила). Примеры
реально заведённых у тенанта `filatov`: `CUSTOMER_PAYMENT`, `CUSTOMER_PAYMENT_EQ`,
`ACQUIRING_FEE`, `BANK_SERVICE`, `SUPPLIER_PAYMENT`.

## 4. Таблицы движのengine (БД тенанта `findir_{slug}`)

### `category_postings` — карта разноски (ступень 2, «куда проводить»)
Одна строка на категорию (`category` unique).
```
category               string(40) unique   -- строка категории (свободная)
counter_account_code   string(35) null     -- корр-счёт ПО КОДУ (общий для тенантов)
flow_info_id           bigint null          -- статья ДДС (id), кладётся на А100-ногу
partner_mode           string(16)           -- from_inn | none
is_active              bool
```
Модель: `app/Models/Tenant/CategoryPosting.php`. CRUD: `CategoryPostingController`
(уникальность `category` проверяется ВРУЧНУЮ на тенантном соединении, т.к.
валидатор `unique:` смотрит дефолтную БД).

### `payment_classification_rules` — правила классификации (ступень 1)
Рождается ПУСТОЙ. Условия (заданные) по AND.
```
direction          string(8)  default 'any'   -- in | out | any
inn                string(20) null            -- точное совпадение ИНН контрагента
purpose_keywords   text null                  -- подстроки через '|' (contains, любая)
has_kbk            bool null                  -- для TAX (шаг 3)
amount_min/max     decimal null
category           string(32)                 -- результат: строка категории
priority           int default 50             -- выше = раньше; первое совпадение
source             string(16) default 'manual'-- manual | learned
hit_count          bigint default 0           -- статистика (read-only в UI)
last_applied_at    timestamp null
created_by         bigint null
is_active          bool
```
Модель: `app/Models/Tenant/PaymentClassificationRule.php`. CRUD:
`PaymentClassificationRuleController`. Приоритеты-бэнды: универсальные ~100,
тенантные 50–89, keyword/role 10–49.

> **Историческая заметка:** в `payment_classification_rules` временно добавлялась
> колонка `counter_bi_id` (override счёта на уровне правила, «Вариант Y»). Затем
> от неё отказались (Путь A: счёт определяется категорией через разноску). Колонка
> удалена. Если она где-то всплывёт — это откат, её быть не должно.

## 5. Конвейер (`app/Services/BankStatementMatcher.php`)

`matchRow()` по шагам:
1. `classify($row)` → категория:
   - `is_self_transfer` → `TRANSFER` (в коде);
   - правила тенанта по убыванию `priority`, первое совпадение
     (`ruleMatches()` проверяет direction/inn/purpose_keywords/has_kbk/amount по AND);
   - иначе `OTHER`.
2. если категория есть в `category_postings` → `applyPosting()`:
   `suggested_counter_bi_id` (счёт по коду), `suggested_flow_id` (статья ДДС),
   `suggested_partner_id` (если `partner_mode=from_inn`);
   иначе fallback (партнёр по ИНН + keyword-флоу).
3. `suggested_expense_id` = `defaultExpenseForFlow(suggested_flow_id)` — статья
   расхода из `info.default_expense_id` подставленной статьи ДДС (для обеих веток).
4. если `is_acquiring_split` + `acquiring_fee` → `applyAcquiringFeeLeg()`:
   подсказки второй операции (комиссии) из разноски категории `ACQUIRING_FEE`
   (константа `ACQUIRING_FEE_CATEGORY`): `suggested_fee_amount`,
   `suggested_fee_bi_id` (П589), `suggested_fee_flow_id`, `suggested_fee_expense_id`.

Поля строки на выходе: `suggested_category`, `suggested_counter_bi_id`,
`suggested_flow_id`, `suggested_partner_id`, `suggested_expense_id`, и (для свода)
`suggested_fee_*`.

Справочники грузятся в конструкторе с graceful fallback: нет таблиц движка —
конвейер идёт по fallback-пути.

## 6. Парсер (`app/Services/ClientBankExchangeParser.php`)

Формат 1C `ClientBankExchange` v1.03, Windows-1251.
- Направление — по `ДатаПоступило` / `ДатаСписано`.
- `is_self_transfer` — `ПлательщикИНН == ПолучательИНН`.
- Контрагент: при `in` — плательщик, при `out` — получатель.
- Отдаёт: `counterparty_inn`, `counterparty_account`, `purpose_raw`, `direction`,
  `is_self_transfer`, `amount`, `doc_date`, `external_id/date`, `note`.
- **Эквайринг-свод (v2):** `extractAcquiringFee()` прогоняет назначение по списку
  паттернов `ACQUIRING_FEE_PATTERNS`. Срабатывание = признак свода. Кладёт в строку
  `is_acquiring_split=true`, `acquiring_fee` (сумма), `acquiring_bank` (метка).
  Сейчас один паттерн (Т-Банк): `Сумма комиссии N руб. K коп.`. Структура массива
  расширяема (новый банк = строка в массиве; позже вынести в конфиг/таблицу).
  На апрельской выписке: 30 строк свода, комиссия извлекается верно, 0 ложных на
  96 обычных клиентских «Пополнение лицевого счёта».
- **Ещё НЕ парсит** `ПоказательКБК` / `СтатусСоставителя` — нужно для TAX (шаг 3).

> **Известная проблема (не закрыта):** файл Альфа-Банка содержит НЕСКОЛЬКО
> `РасчСчет` в одной выгрузке. `buildHeader()` кладёт `РасчСчет` перезаписью →
> запомнит последний. Всплывёт при загрузке Альфы. У Альфы комиссия эквайринга
> идёт ОТДЕЛЬНЫМ документом (не свод) — ей разворот не нужен, закрывается обычными
> правилами по ключевикам «Комиссия к возм» / «Возм. по согл. в СБП».

## 7. Фронт (`front/src/pages/BankStatementPage.jsx`)

Структура операции на строке: `OperationLine` исторически **двунога** — одна
сторона ВСЕГДА А100 (фиксирована, по `direction`), вторая — корр-счёт. Это важно
для понимания сплита (см. ниже).

- `makeDefaultOp()` собирает дефолтную операцию из подсказок матчера.
  info_1 корр-ноги: перевод → касса; `info_1_type=expenses` → `suggested_expense_id`
  (статья расхода); иначе `suggested_partner_id` (партнёр).
- Статья ДДС всегда на А100-ноге (`info_2`). Корр-счёт — на корр-ноге.
- Перевод: А100↔А100, «Перемещение денег» на обеих, касса-получатель по
  `counterparty_account` (code→name→description).
- `handleCounterBiChange` при ручной смене корр-счёта: expenses → статья расхода,
  partner → партнёр по ИНН.
- **ИНН контрагента (v2):** под названием контрагента, копируется по клику
  (`copyInn`/`innCopied`). Назначение платежа — `line-clamp-2` (2 строки, без
  обрезки в одну).
- **Сплит эквайринг-свода (v2):** `makeDefaultOps()` для строки `is_acquiring_split`
  возвращает ДВЕ операции: приход нетто (`makeDefaultOp`) + комиссия (`makeFeeOp`).
  Нога комиссии помечена `_kind='fee'` и рендерится СВОБОДНЫМ режимом (оба счёта —
  редактируемые select'ы, без фиксированного А100): Дт = П589 (`suggested_fee_bi_id`)
  + статья расхода + статья ДДС, Кт = наследует доходный счёт приходной ноги
  (`incomeOp.out_bi_id`). Флаг `_kind='fee'` обрабатывается в 6 местах: рендер,
  3 payload-сборки (не навязывать А100), проверка готовности, контроль остатка.
- **Контроль остатка для свода:** целевая сумма = `amount + suggested_fee_amount`
  (нетто + комиссия = брутто), `targetAmount`. Иначе остаток всегда был бы −комиссия.
- **Готовность строки — единый источник истины (v2):** `StatementRow` сам считает
  `isReady` (учитывает свод/ноги комиссии) и шлёт наверх через `rowReadyMap`.
  Родитель НЕ дублирует логику — `readyRows`/`handleCreate` опираются на `rowReadyMap`.
- **Выборочное создание (v2):** каждая строка может быть «пропущена» (`ignored`,
  кнопка ⊘/↩). Массовое «Снять все»/«Выбрать все» через `forcedIgnored`
  ({value, nonce}) — родитель сигналит, строка синхронизирует локальный `ignored`.
  Дефолт — все выбраны. Кнопка «Создать операции (N)» создаёт только готовые и
  выбранные. Уже созданные строки (`postedIds>0`) массовое переключение не трогает.

`BankStatementController::parse` отдаёт `'rows' => $rows` ЦЕЛИКОМ (без белого
списка полей) — поэтому все `suggested_*` и `is_acquiring_split`/`acquiring_fee`
доходят до фронта.

### Бухгалтерия эквайринг-свода (Т-Банк)
Банк зачисляет НЕТТО (оплаты минус комиссия), комиссия — только в тексте. Из одной
строки — две операции:
```
Оп.1 приход:  Дт А100 ← Кт <доходный счёт по правилу>   сумма = нетто (amount)
Оп.2 комиссия: Дт П589 ← Кт <тот же доходный счёт>        сумма = комиссия
```
Кредит комиссии **наследуется** от счёта прихода. Какой это счёт (А405 или П587) —
определяется ПРАВИЛОМ (что в разноске категории прихода), код одинаков. Проверка
баланса (пример 02.04: нетто 80093.35, комиссия 2534.77): А100 = нетто (сходится с
банком), доходный счёт = брутто, П589 = комиссия, прибыль = нетто. ✅

## 8. Тенант и развёртывание

- Кастомный мультитенант. Центральная БД `findir_central`, тенантные
  `findir_{slug}`. Заголовок `X-Tenant: {slug}`. `TenantService::connect($slug)`
  возвращает `$dbName`, дефолтное соединение НЕ переключает — это делает
  вызывающий код. `TenantController::initTenant()` → `$this->dbName`; модели
  цепляются `(new Model)->setConnection($this->dbName)`.
- Тенантные миграции: `back/database/migrations/tenant/`. Команда
  `tenants:migrate` (флаги `--tenant=`, `--fresh`, `--seed`, `--force`).
- Окружение Docker, PHP-сервис `findir_php`. **Фронт — НЕ в php-контейнере**, лежит
  на хосте в `front/src/` (контейнер `findir_front`, Vite, порт 3000). Хост
  Windows/PowerShell (нет `grep`; для php — `docker exec findir_php sh -c "…|grep…"`,
  для фронта — `findstr` на хосте).
- Рабочий тенант для тестов: `filatov` (БД `findir_filatov`).

Развернуть/обновить тенант:
```
docker exec -it findir_php php artisan tenants:migrate --tenant=filatov --seed
```

Проверка модели в tinker (без HTTP, надёжно):
```
docker exec -it findir_php php artisan tinker
> \App\Services\TenantService::connect('filatov');   // регистрирует соединение
> (new \App\Models\Tenant\CategoryPosting)->setConnection('tenant_tmp')->get();
```
(Если `tenant_tmp` не сконфигурирован — поднять вручную:
`config(['database.connections.tenant_tmp' => array_merge(config('database.connections.mysql'), ['database'=>'findir_filatov'])]);`)

## 9. Что сделано в v2 (поверх фундамента)

### 9.1. Статья расхода (`default_expense_id`) — ✅ ЗАКОНЧЕНО
- Миграция: в `info` добавлена `default_expense_id` (bigint nullable, индекс,
  self-reference на `info.id` типа expenses, БЕЗ FK; стиль как у `parent_id`).
- Модель `Info`: `default_expense_id` в `$fillable` + cast integer.
- `InfoController` (store/update): поле валидируется и сохраняется.
- UI: в карточке статьи ДДС (`InfoPage.jsx`, только `type=flow`) — выпадашка
  «Статья расходов по умолчанию» (список `getInfo({type:'expenses'})`). Плюс
  нередактируемый копируемый `id` в списке и карточке.
- Матчер: `suggested_expense_id` из `flow.default_expense_id`.
- Фронт выписки: статья расхода в info_1 корр-ноги (когда корр-счёт `info_1=expenses`).

### 9.2. Поступления от клиентов — ✅ (конфигурацией)
Закрывается категориями + правилами через UI. Виды: оплата по счёту (контрагент по
ИНН → А405), СБП-приход. Счёт прихода (А405 vs П587) — выбор в разноске категории.

### 9.3. UI управления правилами и разноской — ✅ ЗАКОНЧЕНО
- Бэкенд: модели `PaymentClassificationRule`, `CategoryPosting` + контроллеры CRUD
  + роуты `/classification-rules`, `/category-postings`.
- Фронт: `ClassificationRulesPage.jsx` (одна страница, две секции — разноска
  сверху, правила снизу). API-модули `classificationRules.js`, `categoryPostings.js`.
  Счета — выпадашка по id, СОХРАНЯЕТСЯ код. Категории — свободный ввод + `datalist`
  существующих (защита от опечаток, не запрет). ⚠ если у правила категория без
  разноски.
- Меню: пункт «Настройки» (выпадающий) в `Layout.jsx` → Справочники + Настройка
  правил. «Справочники» убран из верхнего ряда.

### 9.4. ИНН в выписке — ✅
Под контрагентом, копируется по клику. Назначение — в 2 строки.

### 9.5. Сплит эквайринг-свода Т-Банка — ✅ ЗАКОНЧЕНО
Парсер → матчер → фронт (см. §6, §5, §7). Одна строка свода → две операции
(приход нетто + комиссия), нога комиссии в свободном режиме. Проверено на апреле.

### 9.6. Выборочное создание операций — ✅
«Снять все»/«Выбрать все» + поштучный ⊘/↩, дефолт «все выбраны». Для ревью перед
загрузкой. Заодно убрано дублирование логики готовности (`rowReadyMap`).
