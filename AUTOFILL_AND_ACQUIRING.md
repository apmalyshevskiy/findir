# Памятка: автозаполнение выписок и эквайринг-свод

Как при загрузке банковской выписки система сама проставляет контрагента, счёт
и статью ДДС, и как обрабатывается эквайринг (выделение удержанной комиссии).

---

## 1. Общая картина: три стадии

Загрузка файла (`POST /bank-statements/parse`) ничего не пишет в БД — она готовит
данные для формы. Внутри три стадии:

1. **Парсинг** (`ClientBankExchangeParser`) — из 1C-файла (Win-1251) достаём строки:
   направление, сумму, контрагента, ИНН, назначение. Здесь же срабатывает
   **эквайринг-свод** (см. §4).
2. **Классификация** (`BankStatementMatcher`) — для каждой строки подбираем
   контрагента, корреспондирующий счёт и статью ДДС.
3. **Поиск дублей** — по `external_id` + `external_date` ищем уже загруженные
   операции, чтобы не задвоить.

Результат — строки с подсказками (`suggested_*`), которые пользователь
подтверждает или правит на странице выписки.

---

## 2. Стадия 1 — парсинг

Из каждого `СекцияДокумент` достаём:

| Поле выписки | Что становится |
|---|---|
| `Сумма` + `ДатаПоступило`/`ДатаСписано` | `amount`, `direction` (`in`/`out`) |
| `Плательщик1`/`Плательщик` (приход) или `Получатель1`/`Получатель` (расход) | `counterparty_raw` (имя) |
| `ПлательщикИНН`/`ПолучательИНН` | `counterparty_inn` |
| `НазначениеПлатежа` | `purpose_raw` |
| `Номер`, `Дата` | `external_id`, `external_date` |

Особенности:

- **Имя контрагента** читается из поля с цифрой (`Плательщик1`), а если его нет —
  из поля без цифры (`Плательщик`). Это покрывает и Т-Банк (с цифрой), и Альфу
  (без цифры). У имени отрезается хвост « Р/С …».
- **Перевод между своими счетами** определяется самодостаточно: если в документе
  `ПлательщикИНН == ПолучательИНН` → `is_self_transfer = true`.
- **Банк** определяется по полю `Отправитель` (`detectBank`): `Т-Банк` → `tbank`,
  `Альфа-Бизнес Онлайн` → `alfa`, `Сбербанк Бизнес Онлайн` → `sber`. Используется
  для скоупа правил свода (§4).
- **Счёт (касса)** ищется по `info.type=cash` — сопоставление номера счёта из
  выписки с `description`/`code` справочника касс.

---

## 3. Стадия 2 — классификация

Цель: для строки выдать `category`, из неё — корреспондирующий счёт
(`counter_account_code`), статью ДДС (`flow`) и режим подбора контрагента.

Работает в две ступени.

### 3.1 Правила классификации (`payment_classification_rules`)

Определяют, **какую категорию** присвоить строке. Поля правила:

| Поле | Смысл |
|---|---|
| `direction` | `any` / `in` / `out` |
| `purpose_keywords` | подстроки через `\|`; срабатывает, если назначение содержит любую (регистронезависимо, по `contains`) |
| `inn` | привязка к конкретному ИНН контрагента |
| `has_kbk` | признак наличия КБК |
| `amount_min` / `amount_max` | диапазон суммы |
| `category` | какую категорию присвоить |
| `priority` | приоритет (тенантные правила — 50…89) |
| `is_active` | вкл/выкл |

**Срабатывает правило с наибольшим приоритетом среди подошедших (first match wins).**
Поэтому более специфичные правила ставят выше по приоритету, общие — ниже.

> Единственная захардкоженная логика в матчере — `is_self_transfer → TRANSFER`.
> Всё остальное настраивается правилами тенанта, без правки кода.

### 3.2 Разноска по категориям (`category_postings`)

Категория → проводка. Поля:

| Поле | Смысл |
|---|---|
| `category` | ключ (совпадает с `category` из правила) |
| `counter_account_code` | корреспондирующий счёт плана счетов (по коду: `П587`, `П589`, `А405` …) |
| `flow_info_id` | статья ДДС |
| `partner_mode` | `from_inn` (искать контрагента по ИНН) или `none` (не заполнять) |
| `is_active` | вкл/выкл |

Контрагент (`suggested_partner_id`) при `partner_mode=from_inn` ищется в
`info.type=partner` по `counterparty_inn`.

### 3.3 Запасной подбор статьи

Если категория не определилась/без разноски — грубый подбор статьи ДДС по
ключевым словам назначения (`getFlowRules`): например для расхода `комисси` →
административные расходы. Это «лучше, чем ничего», не замена настроенным правилам.

## 4. Эквайринг-свод (выделение комиссии)

### 4.1 Что это

Некоторые банки по операциям эквайринга зачисляют **нетто** (выручка минус
комиссия), а саму комиссию указывают **только текстом** в назначении —
отдельной строки расхода в выписке нет. Чтобы учёт был корректным, такую строку
надо развернуть в **две операции**: приход нетто + комиссия.

«Свод» определяется на **стадии парсинга**, до классификации, потому что это не
вопрос «какая статья», а вопрос «надо ли расщепить строку и на какую сумму».

### 4.2 Где настраивается

Правила свода лежат в таблице `settings`, ключ **`acquiring_fee_rules`** (JSON),
**у каждого тенанта свой набор**. Редактируются на странице «Эквайринг»
(`/acquiring-fee-rules`) или через `GET`/`PUT /settings/acquiring-fee-rules`.

Каждое правило — понятные поля, **без сырого regex**:

| Поле | Смысл |
|---|---|
| `bank` | метка банка (`tbank`/`alfa`/`sber`), сопоставляется с `detectBank` по `Отправитель` |
| `marker` | текст в назначении, **сразу после которого** идёт сумма комиссии |
| `amount_format` | формат суммы: `rub_kop` или `dot` |
| `is_active` | вкл/выкл |

Regex собирается движком из `marker` + `amount_format`, поэтому всегда валиден.

### 4.3 Форматы суммы

- **`rub_kop`** — рубли и копейки словами: `Сумма комиссии 2534 руб. 77 коп.`
- **`dot`** — через точку, с возможными пробелами-тысячами: `К.1794.86`,
  `Комиссия 1 511.16`. Пробелы внутри числа вычищаются; сумма берётся
  **сразу после маркера**, чтобы не перехватить НДС из хвоста строки.

### 4.4 Текущие банки (проверено на реальных выписках)

| Банк | `marker` | `amount_format` | Пример назначения |
|---|---|---|---|
| Т-Банк | `Сумма комиссии` | `rub_kop` | `…Сумма комиссии 3358 руб. 38 коп.…` |
| Альфа | `К.` | `dot` | `…Р.03062026 К.1794.86 в т.ч. НДС 234.86` |
| Сбер | `Комиссия` | `dot` | `…эквайринга. Мерчант №… Комиссия 1 511.16 (в т.ч. НДС 272.40)` |

Скоуп по банку обязателен: маркер «Комиссия» (Сбер) общий, без привязки к
`Отправитель` он сработал бы на чужих выписках. Поэтому правило применяется
только если `detectBank` опознал тот же банк.

### 4.5 Что происходит при срабатывании

Строка помечается `is_acquiring_split=true`, извлекается `acquiring_fee`.
На форме она разворачивается в две операции:

- **приход нетто** — на сумму `Сумма` из выписки, классифицируется обычными
  правилами (доходная категория → счёт доходов);
- **комиссия** — на сумму `acquiring_fee`, через разноску категории
  `ACQUIRING_FEE` (расход, обычно `П589`, статья «Эквайринг»). Кредитовая нога
  комиссии наследует доходный счёт приходной ноги.

## 5. Свод или отдельная комиссия — как отличить

Не всякая комиссия эквайринга — свод. Бывает второй вариант: банк зачисляет
**брутто**, а комиссию списывает **отдельным документом**. Тогда свод не нужен —
это две обычные операции, и обе закрываются правилами классификации.

Пример (Альфа, СБП): приход «Возм. по согл. в СБП…» (полная сумма) + отдельный
расход «Комиссия к возм…». Свод сюда добавлять **нельзя** — иначе создашь
фантомную ногу комиссии и разъедешься по балансу.

**Как проверить перед добавлением банка в свод:** сравнить `Сумма` по приходной
строке с суммой реестра.

- `Сумма ≈ реестр − комиссия` (нетто) → **это свод**, добавляем правило.
- `Сумма ≈ реестр` (брутто), а комиссия идёт отдельным документом → **не свод**,
  правило свода не добавляем; комиссию ловим расходным правилом классификации.

Косвенный, но надёжный признак нетто: сумма комиссий **не входит** в
`ВсегоПоступило`/`ВсегоСписано` заголовка (банк удержал её до зачисления, в
оборотах её нет).

---

## 6. Бухгалтерская картина свода

На примере: реестр 60000.00, комиссия 1794.86, зачислено нетто 58205.14.

- приход нетто: Дт `А100` (касса) — Кт `П587` (доходы) на 58205.14;
- комиссия: Дт `П589` (расходы) — Кт `П587` (доходы) на 1794.86.

Итог по `П587` = 58205.14 + 1794.86 = 60000.00 — полная выручка по реестру.
То есть доход признаётся в брутто, а комиссия отражается отдельным расходом.

---

## 7. Как добавить новый банк со сводом

1. **Определить тип.** По реальной выписке проверить нетто/брутто (§5). Если
   брутто с отдельной комиссией — свод не нужен, хватит правил классификации.
2. **detectBank (код).** Добавить ветку распознавания банка по `Отправитель` в
   `ClientBankExchangeParser::detectBank` (требует деплоя — это единственная
   часть свода, что живёт в коде).
3. **Правило (настройка).** На странице «Эквайринг» добавить строку: банк,
   маркер (текст перед суммой), формат (`rub_kop`/`dot`). Деплой не нужен.
4. **Проверить** загрузкой реальной выписки: комиссия извлеклась верно и не
   совпала с НДС; ложных срабатываний на других банках нет.

## 9. Ключевые принципы (чтобы не сломать)

- **Свод и классификация — разные стадии.** Свод (расщепление строки + сумма
  комиссии) — на парсинге. Классификация (счёт/статья) — после. Не смешивать.
- **Сырой regex пользователю не выдаём.** Только `marker` + `amount_format`,
  движок собирает выражение сам — это безопасно.
- **У правил свода нет фолбэка в код.** Источник правды — `settings`. Если ключа
  нет или JSON битый — свод просто не выполняется (выписка парсится без
  расщепления), парсинг не падает.
- **Скоуп по банку обязателен** для общих маркеров (например «Комиссия»).
- **Перед добавлением банка — проверь нетто/брутто.** Ошибка здесь даёт
  фантомную комиссию и расхождение баланса.
